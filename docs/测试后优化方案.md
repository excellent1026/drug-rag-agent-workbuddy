背景：首轮测试完成，针对「漏召回、幻觉、响应性能、面试严谨性」四方面给出优化方案。 配套：科普解读Agent 提示词已补存至 03_Agent提示词/科普解读Agent_系统提示词.md，三 Agent 现已齐全。

一、切片策略优化——减少漏召回
漏召回的 4 个根因
固定 600 字符硬切，把一条完整信息（如某药的禁忌条目）拦腰切断，向量只能命中半个意思。
纯向量检索对「同义不同词」不敏感（如「高血压」vs「血压偏高」），关键词检索也各有盲区。
药品别名/商品名未归一化（「拜阿司匹灵」vs「阿司匹林」），召回直接扑空。
章节标题信息在切片时丢失，检索结果缺少「上下文锚点」。
优化措施（改哪里 → 改成什么 → 为什么）
措施	现状	调整为	作用
切分方式	固定 600 字符硬切	按章节标题结构化切分，章节内按句号切	每条信息完整不跨块
父子 chunk	无	小 chunk（300~500 字）用于检索，父 chunk（整个章节）用于返回给 LLM	检索精准、上下文完整
重叠窗口	80 字符	100 字符，且按句对齐（不足一句补一句）	减少跨块语义断裂
检索算法	纯向量	混合检索 = 向量 + BM25 关键词，加权融合	补上同义词、专有名词召回
别名归一化	无	检索前把商品名→通用名映射（建别名表）	避免别名扑空
召回参数	top_k=5~8	top_k=8~10 + 简单 rerank（按章节相关性排序）	提升召回率再择优
章节前缀	部分保留	每个 chunk 强制带「药品名 + 章节标题」前缀	提供上下文锚点
一句话结论：漏召回的本质是「切块太碎 + 检索太单一」，解法是结构化切分 + 父子 chunk + 混合检索 + 别名归一化四件套。

二、Prompt 优化——进一步降低幻觉
检索Agent（已较严，加一道自检）
增加输出前自检指令：「输出前逐句检查，凡无法在输入片段中逐字定位的表述，一律删除」。
增加反例示例（few-shot）：给 1 个「错误示范（编造剂量）」+ 1 个「正确示范」，让模型学会边界。
科普解读Agent（在现有 6 条规则基础上加 3 条）
强制引用回填：每个【禁用】【慎用】【常见不良反应】标签条目后，加 （出处：【章节名】），保证每句可溯源。
不确定即省略：原文表述模糊、无法明确归入某个标签时，不强行归类，宁可少写不写错。
输出前自检：先自查「这一条是否在输入原文中有对应」，无对应则删除，再输出最终结果。
通用参数与机制
temperature 调低至 0~0.2：科普转述是低创意任务，低温大幅降低自由发挥。
结构化约束优先：用固定标签（禁用/慎用/不良反应…）框住输出，压缩自由发挥空间。
链式校验：解读完成后，可让解读Agent「回读原文，逐条核对要点是否都有据可依」，不一致即修正。
一句话结论：降幻觉靠三件事——引用回填（可溯源）+ 反例示范（教边界）+ 低温 + 结构化标签（压缩发挥空间）。

三、高频问答缓存思路（Java + Redis，简历加分项）
3.1 为什么值得做
药品说明书类问答高度稳定、重复率高（「阿司匹林副作用」「XX 和 YY 能不能一起吃」是高频问题）。缓存可显著降低重复 LLM 调用成本与响应延迟，同时是一个天然的「高并发系统设计」面试素材。

3.2 架构（Cache-Aside + 三防）
用户提问 → Java后端 → 问题归一化 → 缓存Key
                              ↓
                   布隆过滤器：药名是否存在？
                       │不存在 → 直接返回固定话术（防穿透）
                       │存在
                       ↓
                   Redis缓存：命中？→ 直接返回
                       │未命中
                       ↓
               分布式锁（防击穿）+ 双重检查
                       ↓
              调用 RAG 三Agent 工作流
                       ↓
           写回 Redis（TTL + 随机抖动，防雪崩）
           空结果也缓存（短 TTL，防穿透）
                       ↓
                     返回
3.3 关键设计点
问题	现象	方案
缓存穿透	查一个不存在的药，每次都打到 LLM	①布隆过滤器拦截不存在药名；②空结果也缓存（短 TTL，如 60s）
缓存击穿	热点 key 过期瞬间大量并发打到后端	互斥锁（分布式锁）+ 双重检查，只放一个请求去重建缓存
缓存雪崩	大量 key 同一时间过期，后端被打爆	TTL 加随机抖动（如 7天 ± 1小时），避免同时失效
缓存 Key 设计：drug:qa:{md5(规范化问题)}，规范化 = 去空格/标点 + 药名归一化 + 意图归类，保证「阿司匹林副作用」「阿司匹林有什么副作用」命中同一 key。
TTL 策略：说明书类内容稳定，TTL 设 7 天；但知识库「版本日期」更新时主动失效对应 key。

四、项目局限说明（面试主动说，显严谨）
主动说明的局限清单
知识库规模有限：仅覆盖部分慢病常用药说明书 + 少数指南，不是全药品覆盖，冷门药、新药会查不到。
不能做诊断与诊疗决策：定位是科普，明确不替代医生药师，不判断"能不能吃"、不给剂量/换药建议。
数据版本存在滞后：依赖公开说明书/指南版本，修订更新存在时间差，需注明「以最新版说明书为准」。
联用只覆盖已记载的相互作用：知识库「未记载 ≠ 安全」，可能漏掉临床中真实存在但资料未收录的相互作用。
转述存在信息损耗：通俗化过程可能丢失原文细节，因此每条都保留「文档+章节」出处供回溯原文。
检索质量影响上限：RAG 效果受切片与检索算法制约，可能漏召回，仍在通过混合检索等持续优化。
面试话术示例（主动说，先扬后抑）
「这个项目我最清楚它的边界——它做的是『科普检索 + 合规提示』，不是医疗产品：知识库只覆盖慢病常用药、明确不做诊断、联用风险只提示知识库已记载的相互作用。正因为清楚边界，我才在合规护栏上花了最多精力，比如强制出处标注、空结果固定兜底、禁止编造。我觉得这类项目最重要的不是"看起来能做什么"，而是"知道自己不能做什么"。」

这段话的加分点：主动暴露局限 + 说明为应对局限做了什么 + 体现工程严谨性。
